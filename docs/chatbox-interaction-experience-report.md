# Chatbox 交互体验优化报告


## 0. 当前进度更新（2026-06-02）

本轮已经完成会话组织和部署稳定性相关优化，因此本文后续章节中原先标为“待补”的部分需要按以下状态理解。

已完成：

- 会话时间分组和分组折叠。
- 会话收藏、归档、标签、置顶。
- Active / Archived 视图切换。
- 收藏筛选和标签筛选。
- 置顶会话独立 Pinned 分组。
- RichMarkdown 视口懒渲染，降低长会话首屏渲染压力。
- native 部署启动、停止和状态检查脚本稳定性增强。

仍待优化：

- 左侧会话搜索、命中片段和点击跳转。
- 当前会话内全文搜索和消息跳转。
- 会话组织操作的 undo toast、批量标签管理、mode/file/failed-run badges。
- 长消息折叠、消息内部目录、代码行号、Mermaid 放大/下载。
- 错误恢复面板和 Council Run Summary。

## 1. 报告目标

本文从一个成熟 chatbox 产品的功能和体验角度，按模块分析当前系统还可以补充和优化的交互能力。重点不重复后端上下文管理细节，而是关注用户在日常使用中的效率、可理解性、可靠性和长对话舒适度。

当前项目已经具备：

- quick mode 和 council mode。
- 文件对话。
- 会话上下文策略、预览、复盘。
- 消息 pin/exclude。
- retry/resume/fork。
- Markdown、表格、代码、LaTeX、Mermaid 富内容渲染。
- 深色模式和 turn 导航。
- 会话时间分组折叠、收藏、归档、标签、置顶和 Archived 视图。
- RichMarkdown 视口懒渲染。

后续体验优化应围绕三类目标展开：

- 降低用户理解系统状态的成本。
- 提升长对话和复杂输出的操作效率。
- 让失败、等待、重试、分叉等非理想路径也可控。

## 2. 总体体验原则

### 2.1 默认简单，高级能力可展开

chatbox 的主界面应保持轻量，用户默认只需要输入、阅读、继续提问。上下文策略、审计、模型运行细节、token 预算等高级能力应折叠展示，在需要诊断或调优时展开。

建议：

- 主聊天区域默认只展示必要信息。
- 每条消息的高级操作收进 hover toolbar 或更多菜单。
- context audit、replay、run metadata 默认折叠。
- 复杂设置集中在侧栏或会话设置面板。

### 2.2 让系统状态始终可见

用户需要知道系统当前是否在：

- 等待模型。
- 上传/解析文件。
- 调用 council 多阶段流程。
- 重试某条历史消息。
- 恢复中断任务。
- 使用了历史上下文。
- 因预算限制裁剪了上下文。

建议：

- 用轻量状态条展示当前任务状态。
- council mode 展示阶段进度。
- long-running 操作提供取消、恢复或后台继续。
- 上下文裁剪用明确但不打扰的提示。

### 2.3 长对话要支持定位、压缩和回溯

长对话中最大的问题不是“能不能显示”，而是“用户能不能快速找回关键 turn”。

建议：

- 保留当前 turn 导航。
- 增加会话内搜索。
- 增加消息目录或章节视图。
- 支持把某个 turn 折叠成摘要。
- 支持收藏/标记关键 turn。

## 3. 会话列表与会话组织

### 3.1 当前价值

会话列表是用户找回历史工作的入口。对于本项目，conversation 不只是普通聊天记录，还包含上下文策略、文件、memory、fork 分支和 council run 审计。

### 3.2 可优化点

#### 会话标题质量

问题：

- 自动标题如果过泛，会话列表很快难以区分。
- council mode 的标题可能没有体现任务阶段或文件主题。

建议：

- 标题生成使用当前用户问题、文件名、最终回答主题共同决定。
- 标题旁展示模式标签：Quick / Council。
- 文件会话显示附件数量或主文件名。
- 标题支持手动重命名。

#### 会话分组

当前状态：基础版已实现。

已完成：

- 按时间分组和分组折叠。
- 收藏会话。
- 归档会话和 Archived 视图。
- 标签编辑和标签筛选。
- 置顶会话 Pinned 分组。

后续建议：

- 标签颜色和标签管理。
- 项目/主题分组。
- mode、文件、失败 run badges。
- 归档/置顶/收藏操作的撤销提示。

#### 会话搜索

问题：

- 当前有历史搜索能力，但可以更产品化。

建议：

- 左侧搜索同时匹配标题、消息内容、文件名、memory。
- 搜索结果显示命中片段。
- 点击结果跳转到具体消息。
- 支持搜索过滤：quick/council、有文件、有 pin、有失败 run。

#### Fork 分支展示

问题：

- fork 如果只表现为普通新会话，用户难以理解分支关系。

建议：

- 会话列表中显示分叉标识。
- 会话详情里显示“来自哪个会话的哪条消息”。
- 支持打开分支树。
- 支持两个分支对比。

### 3.3 优先级

- P0：会话内搜索跳转、左侧会话搜索产品化。
- 已完成：会话重命名、时间分组折叠、收藏、标签、归档、置顶。
- P1：mode/file/failed-run badges、标签颜色和撤销提示。
- P2：分支树和分支对比。

## 4. 输入区体验

### 4.1 当前价值

输入区是 chatbox 的主操作入口。本项目比普通 chatbox 多了模式选择、文件上传、上下文预览等能力，因此输入区需要既强大又不拥挤。

### 4.2 可优化点

#### 模式选择

问题：

- quick mode 和 council mode 可能穿插出现，用户需要清楚当前消息会用哪个模式。

建议：

- 输入区使用 segmented control 切换 Quick / Council。
- 模式旁显示简短成本提示：低延迟 / 多模型综合。
- 最近一次使用的模式按会话保存。
- 对文件消息也明确显示将使用哪个模式。

#### 上下文状态提示

问题：

- 用户需要知道“下一条消息会带多少上下文”，但不应被详细技术信息打扰。

建议：

- 输入区只显示简短提示：例如“将包含 8 turns、2 pinned、1 memory”。
- 点击后打开 context preview。
- 当上下文被裁剪时显示提示：“部分较早历史已由摘要代替”。

#### Prompt 编辑能力

问题：

- 用户经常需要修改上一条问题或延续复杂任务。

建议：

- 支持编辑并重发最近用户消息。
- 编辑历史消息时提示会截断后续回答。
- 支持从任意用户消息 retry with edit。
- 支持草稿自动保存。

#### 快捷操作

建议：

- Enter 发送，Shift+Enter 换行。
- Cmd/Ctrl+Enter 强制发送。
- Esc 取消当前请求。
- `/` 命令菜单：切换模式、清空、预览上下文、添加 memory。
- 支持 prompt 模板。

#### 文件上传入口

建议：

- 拖拽上传。
- 粘贴图片上传。
- 文件上传前显示解析类型。
- 大文件显示解析进度。
- 文件失败时给出明确原因。

### 4.3 优先级

- P0：模式 segmented control、草稿保存、编辑并重发。
- P1：快捷命令菜单、拖拽/粘贴上传。
- P2：prompt 模板、变量化 prompt。

## 5. 消息阅读与长回答操作

### 5.1 当前价值

当前已支持富 Markdown、代码、表格、公式、Mermaid 和 turn 导航。这已经覆盖了复杂回答的核心阅读需求。

### 5.2 可优化点

#### 消息级工具栏

建议每条消息提供统一工具栏：

- 复制全文。
- 重新生成。
- 编辑并重试。
- pin/unpin。
- include/exclude context。
- fork from here。
- 查看上下文 replay。
- 折叠/展开。

工具栏建议 hover 或点击更多按钮出现，避免默认界面拥挤。

#### 长消息折叠

问题：

- council mode 的输出可能很长。

建议：

- 超过一定高度的消息默认显示“展开全部”。
- 支持只折叠代码块、Mermaid 图、表格。
- 支持“只看最终答案”与“显示 council 过程”切换。

#### 消息目录

建议：

- 自动提取 assistant 消息中的 Markdown heading。
- 在消息右侧或浮动菜单展示目录。
- 点击目录跳转到消息内部 heading。

#### 会话内搜索

建议：

- 支持全文搜索当前会话。
- 命中高亮。
- 上一个/下一个命中跳转。
- 支持只搜用户消息、助手消息、代码块、文件名。

#### 引用与来源

建议：

- 对文件问答显示引用的文件片段。
- 对历史上下文显示来自哪条 message 或 memory。
- 对 council 最终回答显示综合来源：哪些模型贡献了关键观点。

### 5.3 优先级

- P0：消息工具栏、会话内搜索、编辑并重试。
- P1：长消息折叠、消息内部目录。
- P2：回答引用来源和 council 贡献来源。

## 6. 富内容组件体验

### 6.1 Markdown 和普通文本

当前富 Markdown 已能满足基本阅读。后续重点是降级和复制体验。

建议：

- 普通 text 不做语法高亮。
- Markdown 渲染失败时保留原文。
- 支持复制 rendered text 和 raw markdown 两种模式。
- 支持导出单条回答为 Markdown。

### 6.2 表格

当前支持 Markdown 表格和复制。后续可以增强为更接近数据工具的体验。

建议：

- 复制 Markdown。
- 复制 CSV。
- 下载 CSV。
- 宽表横向滚动。
- 表头 sticky。
- 大表格默认折叠。
- 表格内搜索。
- 表格排序。

推荐技术：

- 轻量阶段：继续使用 Markdown table + 自定义 copy。
- 增强阶段：`@tanstack/react-table`。
- 导出：Papa Parse / SheetJS。

### 6.3 代码块

当前支持 highlight.js 和复制。后续可以优化代码阅读。

建议：

- 行号。
- 长代码折叠。
- 复制指定代码块。
- 下载为文件。
- Diff 专用样式。
- 语言识别和语言切换。
- light/dark 主题精确绑定。

推荐技术：

- 当前保持 `highlight.js`，轻量可靠。
- 对高质量主题可切换到 Shiki。
- 对可编辑代码再引入 Monaco，不建议默认引入。

### 6.4 Mermaid

建议：

- Mermaid 默认折叠大图。
- 支持放大查看。
- 支持复制 SVG。
- 支持下载 PNG/SVG。
- 渲染失败显示原始代码和错误。

推荐技术：

- Mermaid dynamic import。
- SVG 缓存。
- 大图用 `requestIdleCallback` 延迟渲染。

### 6.5 LaTeX

建议：

- inline 和 block 公式继续使用 KaTeX。
- 渲染失败显示原始公式。
- 支持复制公式源码。
- 长公式横向滚动。

推荐技术：

- KaTeX 适合当前项目。
- MathJax 仅在需要更广 TeX 兼容性时考虑。

### 6.6 图片和多模态输出

建议：

- 用户上传图片显示缩略图。
- 点击查看大图。
- 支持复制图片。
- 支持删除单个附件。
- 图片进入上下文时显示状态：已包含 / 被预算排除 / 仅保留引用。

## 7. 上下文透明度与控制体验

### 7.1 当前价值

当前已有 context preview、replay、policy、memory、pin/exclude，这是区分普通 chatbox 和专业本地 chatbox 的关键能力。

### 7.2 可优化点

#### 上下文摘要可解释

建议：

- 摘要显示来源范围：由 message 1-20 生成。
- 摘要显示更新时间。
- 摘要支持手动编辑。
- 摘要 diff 显示新增/删除内容。

#### 上下文预算可视化

建议：

- 用条形图展示 summary、recent、pinned、memory、file 占比。
- 显示哪些内容因为预算被裁剪。
- 支持“为什么没有包含这条消息”的解释。

#### Memory 建议流

建议：

- 模型可建议“是否记住这条偏好/事实”。
- 用户确认后加入 memory。
- memory 显示来源和置信度。
- 支持禁用某条 memory。

#### Pin/Exclude 的反馈

建议：

- 被 pin 的消息有清晰标记。
- 被 exclude 的消息视觉弱化，但不隐藏。
- 输入区上下文提示中统计 pin/exclude。

### 7.3 优先级

- P0：摘要来源范围、预算裁剪原因。
- P1：memory 建议确认流。
- P2：上下文 drift 可视化 diff。

## 8. 文件对话体验

### 8.1 当前价值

文件模式已经能进入 quick/council 对话。后续体验重点是“文件是否被理解、是否进入上下文、引用了哪里”。

### 8.2 可优化点

#### 文件解析状态

建议：

- 上传中。
- 解析中。
- 可用于上下文。
- 解析失败。
- 文件过大，仅部分进入上下文。

#### 文件引用展示

建议：

- 回答中显示引用片段。
- 点击引用定位到文件 chunk。
- 文件预览支持页码、行号或表格区域。

#### 文件管理

建议：

- 会话文件列表。
- 删除文件。
- 重新解析文件。
- 文件重命名。
- 文件是否默认进入后续上下文的开关。

#### 多文件问答

建议：

- 让用户选择本轮使用哪些文件。
- 显示每个文件占用上下文预算。
- 对多个文件做对比摘要。

### 8.3 推荐技术

- PDF：pypdf、pdfplumber。
- Office：python-docx、openpyxl。
- 表格：pandas。
- OCR：PaddleOCR、Tesseract。
- 文件索引：Qdrant、pgvector、LanceDB。

## 9. Council Mode 体验

### 9.1 当前价值

Council mode 的优势是多模型视角和综合判断，但交互复杂度更高。用户需要知道每个阶段在做什么，而不是只看到一个等待 spinner。

### 9.2 可优化点

#### 阶段进度

建议：

- Stage1：候选回答生成。
- Stage2：交叉评价。
- Stage3：主席综合。
- 每个阶段展示完成数、失败数、当前模型。

#### 中间结果控制

建议：

- 用户可选择隐藏/显示中间过程。
- 默认只看最终答案，高级用户展开 council details。
- 某个模型失败时显示 fallback 或跳过原因。

#### 模型贡献解释

建议：

- 最终回答中展示采用了哪些模型观点。
- Stage2 排名和主席综合之间建立可视关系。
- 支持复制单个模型回答。

#### 成本和延迟提示

建议：

- 发送前提示 council mode 会调用多个模型。
- 展示预计耗时或历史平均耗时。
- 完成后展示实际耗时。

### 9.3 优先级

- P0：阶段进度和失败状态。
- P1：默认折叠 council details。
- P2：模型贡献解释和成本估算。

## 10. 错误、失败与恢复体验

### 10.1 当前价值

当前已有 fallback、retry 和 resume。后续需要让用户更清楚地理解失败类型和可操作选项。

### 10.2 可优化点

#### 错误分类

建议错误分为：

- API key/config 错误。
- provider 网络错误。
- provider 限流。
- 模型不可用。
- context 超限。
- 文件解析失败。
- 客户端断开。

#### 错误动作

不同错误给不同操作：

- 重试同模型。
- 使用 fallback 模型。
- 切换 quick mode。
- 缩减上下文。
- 移除文件。
- 恢复中断 run。

#### 用户可见诊断

建议：

- 普通用户看到简短错误。
- 展开后看到 provider、model、attempts、latency、错误摘要。
- 不直接暴露敏感 payload 或 API key。

### 10.3 优先级

- P0：错误分类和操作按钮。
- P1：失败 run 诊断面板。
- P2：自动建议修复方案。

## 11. 模型与设置体验

### 11.1 可优化点

#### 模型选择

建议：

- quick model、council candidates、chairman model 分区配置。
- 每个模型显示 provider、上下文窗口、是否支持图片、价格/延迟提示。
- 无效配置即时提示。

#### 会话级模型配置

建议：

- 全局默认模型。
- 每个 conversation 可覆盖模型设置。
- retry 时可临时换模型。

#### 模板化 council 配置

建议：

- 快速模板：快速、平衡、严谨、低成本。
- 每个模板对应不同模型数量和主席模型。

### 11.2 推荐技术

- 前端表单：React controlled form。
- 配置校验：Pydantic schema。
- provider metadata：本地模型能力表。

## 12. 性能与延迟体验

### 12.1 当前风险

富内容组件和长对话会增加前端负担。Mermaid、KaTeX 和代码高亮虽然按需加载，但长消息多时仍可能卡顿。

### 12.2 可优化点

#### 渲染性能

建议：

- 消息列表虚拟滚动。
- 大代码块折叠。
- Mermaid 进入视口后再渲染。
- replay panel 展开后再加载。
- Markdown AST 缓存。

#### 发送延迟

建议：

- context preview 不阻塞发送。
- 文件解析显示后台进度。
- quick mode 优先低延迟。
- council mode 流式展示阶段结果。

#### Bundle 体积

建议：

- Mermaid、KaTeX、highlight.js 继续 dynamic import。
- 按语言拆分高亮包。
- 只注册常用语言。

### 12.3 推荐技术

- `@tanstack/react-virtual`。
- IntersectionObserver。
- React memo/useMemo。
- Vite manualChunks。
- requestIdleCallback。

## 13. 可访问性与键盘体验

### 13.1 可优化点

建议：

- 所有按钮有 accessible label。
- 图标按钮有 tooltip。
- 输入区、会话列表、消息列表支持键盘导航。
- 深色模式对比度检查。
- 错误信息不只依赖颜色表达。
- Mermaid 图提供源码 fallback。
- 代码块和表格支持键盘复制操作。

### 13.2 推荐技术

- axe-core。
- Playwright accessibility checks。
- Radix UI 或 Headless UI 作为复杂控件基础。

## 14. 移动端与响应式体验

### 14.1 可优化点

建议：

- 移动端侧栏变为 drawer。
- context 面板默认隐藏。

## 18. 结论

当前项目已经具备一个高级 chatbox 的核心基础：有状态会话管理、上下文透明度、富内容渲染和 council mode 多模型流程。接下来最值得补充的是围绕用户日常路径的交互效率：

- 找得到历史。
- 看得懂系统用了哪些上下文。
- 长回答能快速定位和折叠。
- 文件和图表有清晰状态。
- 失败时知道下一步能做什么。
- quick/council 的成本和延迟差异清楚可见。

优先完成 P0 和 P1 后，这个系统会从“功能完整”进一步接近“高频使用舒服、复杂任务可控”的 chatbox。
